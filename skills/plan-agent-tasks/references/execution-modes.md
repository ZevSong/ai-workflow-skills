# 执行模式约定

本约定用于生成 Main 卡和会话提示词。将本任务适用的规则实例化到卡片中，不要求后续会话读取个人 Skill 的安装目录。

## 选择与启动

支持三种模式：`auto`（全自动）、`semi-auto`（半自动）、`manual`（人工）。模式控制由谁推进会话，不改变任务范围、验收、独立审查及项目权限，也不决定模型资源或 Fast。模型与速度是另外两个轴，见 [模型资源与速度策略](model-and-speed-policies.md)。

- 优先使用本轮明确选择或仍适用于本任务的既有用户选择。没有选择时沿用 `manual`，在交付中说明默认值；不把“生成自动模式计划”解释为“立即执行计划”。
- 只有任务较多时主动提出半自动选项：参考信号为至少 5 个 Worker 任务，或至少 3 个有先后依赖的执行批次；结合可验收成果判断，不把数字当硬性门槛。先给具体阶段建议，再让用户选择；用户未选择前保持原模式。已经选定全自动或人工时，不因数量增加重复打断询问。
- 用户直接指定半自动时不受任务数限制。按可验收成果分成少量大阶段，不以每个 Worker/Reviewer 作为阶段，也不强制凑固定阶段数。
- 总卡登记模式、选择来源、执行载体、Main 会话名、并行上限、模式授权范围与停止点。半自动另有阶段清单：阶段 ID/名称、所含 Task、进入条件、交付与验收、下一阶段范围。
- 生成结束只交付材料；用户发送本任务已实例化的 Main 启动提示词后才进入执行。提示词必须用自然语言写明实际模式和调度授权，不能只放一个 `auto` 字段或要求 Main 从模糊的“按计划执行”推断授权。

## 三种模式的行为

| 模式 | Main 启动后的职责 | 下一会话如何启动 | 何时等用户 |
| --- | --- | --- | --- |
| 全自动 | 持续调度就绪任务、独立审查、修复、复审与已授权集成，直到约定停止点 | Main 自动创建或续接计划内的命名会话并发送具体提示词 | 真实阻塞、需求/范围变化、尚未取得的适用人类批准或额外操作授权 |
| 半自动 | 在已获准阶段内按全自动规则运行，阶段结束提交可验收结果 | Main 只自动调度当前获准阶段；下一阶段须用户明确确认 | 每个阶段交界，以及与全自动相同的真实阻塞和批准条件 |
| 人工 | 核对当前材料、给出下一步、会话名称、启动条件与可复制提示词 | 用户逐个创建或续接会话；Main 不自动发送会触发执行的消息 | 每次需要启动、返修、复审或继续另一会话时 |

人工模式允许用户启动的 Worker/Reviewer 完成本卡已授权工作；不是每个编码或测试步骤都询问。所有模式下，Worker/Reviewer 完成后写交付材料，由 Main 核对；它们不自行启动下一个角色、扩大委派或越过阶段界限。自动调度权集中在 Main。

## 全自动调度与恢复

将以下规则按本任务环境写进 Main 卡：

1. 从总卡、活动状态来源和报告核对真实进度、材料可用性与已有会话，先恢复再派工。会话名称是人类标识，运行中登记工具返回的会话 ID、角色、Task、阶段、状态和证据入口；ID 未创建前留为待创建，不虚构。运行状态只写项目已有权威位置，或一个明确约定、由 Main 单独维护的相对路径文件，不另建重复看板。
2. 计算已满足前置条件、位于当前授权范围且没有并行写入冲突的任务；在用户/环境允许的并发容量内按名称新建 Worker。每个写入 Worker 使用独立 branch/worktree；支持由工具准备或由会话先准备，准备完成前不得写产品文件。不得假定创建子 Agent 自动获得隔离 worktree。
3. 派工使用对应的独立完整提示词，并显式传入总卡已解析的模型、推理强度和工具支持的服务层参数；不能省略后继承 Main。创建后记录计划与实际绑定，等待或读取实际工具状态，不能把派工成功当成交付完成。优先事件等待/紧凑状态查询，保持用户可见进展，不靠反复聊天追问形成事实记录。
4. Worker 交付及所需材料就绪后，启动独立 Reviewer；Reviewer 不继承作者工作聊天，使用明确需求、卡片、差异和证据。未通过时续接原 Worker 修复，再续接原 Reviewer 复审。报告必须对应本次实现，不能让旧结论覆盖新修改。
5. 只有全部所需前置、审查和适用批准满足后才进入依赖任务或集成；语义修复交回 Worker。正常待审、测试失败可修复或容量不足不自动要求人类接管，Main 应继续范围内可推进工作。
6. Main 中断或替换后，核对登记的实际会话状态和未完成动作，避免重复创建或重发已完成任务。创建结果不确定时先查询确认，不盲目重试产生重复会话。未拿到真正可用的会话 ID 前不发送后续执行消息。
7. 卡片写清合理的重试/修复停止条件：同一阻塞反复出现且无新证据或可行方案、需求需要改变、材料/权限不可取得时，汇总已做工作、具体阻塞和所需决定；不能无限创建新会话或重复同一失败动作。无依赖的已授权工作可继续。

## 半自动阶段门禁

用户发送半自动 Main 启动提示词，视为授权启动其中明确列出的首阶段。每一后续阶段必须获得用户针对该阶段的明确确认；首次选择半自动不等于批准后续所有阶段。

Main 在阶段末先完成本阶段所需独立审查与验收，交付「已完成结果、实际验证、未解决问题、下一阶段的目标/任务/影响」，再请求进入指定下一阶段。将确认来源和实际批准的阶段记入权威状态；沉默、等待超时、工具默认预选或仅收到 Reviewer PASS 都不构成批准。

获批前不得创建下一阶段会话、向其发送执行提示词或以预热名义启动工作；可以只读准备下一阶段说明。当前阶段失败时，在该阶段内修复/复审或报告阻塞。跨阶段返工先标记受影响结果与审查失效，向用户说明返工范围并取得确认，再调整阶段；不能用返工绕过阶段边界。

半自动流程图使用按阶段分组的 `subgraph`，交界显式设置“用户确认进入 Sxx”条件节点。每个后续阶段交付一个已实例化、可复制到原 Main 的确认提示词，包含阶段 ID/名称、Main 名称、模式、卡片仓库和相对路径、范围及阶段末停止点。

## 运行能力与权限边界

Main 启动时检查当前宿主提供且允许使用的创建/委派、续接、等待/状态、命名、隔离、准确模型选择和单会话服务层能力；以当时工具契约为准。Skill 是执行规则，不是常驻调度服务，不能承诺应用关闭后继续调度，也不会自行创建定时任务或安装第三方 Orchestrator。

- Desktop 独立任务与会话内部子 Agent 是不同执行载体。沿用用户要求的独立会话；只有用户接受子 Agent 载体且宿主允许时才采用内部委派，并明确显示该选择，保持独立审查上下文和写入隔离。不要把两种载体说成完全相同。
- 若宿主允许按用户明确请求创建独立 Desktop 任务，Main 提示词须明确请求创建总卡登记的命名任务并允许续接；运行时从项目工具定位仓库、遵守其 worktree/会话 ID 规则。宿主将当前任务委派限定为子 Agent 时，不能用提示词覆盖此限制。
- 所需载体或调度能力不可用时，如实报告具体缺口，保留完整人工启动提示词，请用户决定采用可用载体或人工模式；未获确认不静默降级。不把本机工具可用推断为所有机器可用，也不硬编码机器路径、项目 ID 或会话 ID。
- 若宿主不能按会话指定模型，自动模式不得以省略参数继续创建；保留提示词和准确绑定，报告该派工能力缺口。若仅缺少单会话 Fast，则按模型与速度策略回退标准服务层，不改变模型，也不把 `critical-path` 静默扩成全局 Fast。
- 自动模式授权本任务计划内的会话创建、续接和范围内执行；推送、Issue/PR 写入、合并、发布等按本次用户已有授权与项目规则判定，不重复请求已授予的权限，也不由“全自动”推导无限授权。项目要求的非作者人类审查保留，Main 负责推进到该门禁并提供可审查成果。
- 将任务适用的证据读取、数据访问和授权限制传入所有角色及恢复入口；调度、状态核对、审查和集成都不能引入被禁止的检查或绕过限制。

三种模式下完整保留每个角色的短提示词。全自动/半自动标明由 Main 调用、供用户审阅或故障恢复；人工标明由用户逐个粘贴。不要把自动模式交付缩减为只给 Main 一个提示词。
