## 路径锚点与多机器分发

每个代码/文档引用都说明所属仓库。仓库标识使用项目已有名称或 organization/repository；它是身份，不是本机目录名。代码路径、命令工作目录及卡片入口相对于其所属仓库根；Markdown 文件内的相对链接则相对于该文件。

跨仓引用示例：

```yaml
implementation_repository: task-api
command_cwd: .
card_repository: task-specs
card_path: task-cards/JOBS-17/workers/JOBS-17-API.md
contract_repository: task-specs
contract_path: contracts/job-status.md
```

在每台机器运行时分别定位这些仓库。不能把跨仓引用写成假定目录相邻的 `../task-specs/...`，也不能把 task-specs 的路径解释为 task-api 根内文件。不要把仓库标识伪装成一个未经定义的文件系统 URI。

产物内禁止盘符绝对路径、UNC 网络路径、以根目录开始的本机文件路径、file URI，以及通过 home/用户目录/环境变量重新嵌入机器路径。此规则覆盖正文、Markdown 文件链接、命令、代码围栏和提示词；普通 HTTP API 路由和真实远程 Issue/PR URL 不是本机文件路径。相对链接允许文件所在目录内必要的 `../`，但不得借此猜测另一克隆的位置。

在提示词中明确角色、Task ID、目标仓库、卡片仓库和卡片相对路径。工作目录为实施/审查 worktree 的仓库根，不能指向 Main 的共享工作区。每段提示词自己声明仓库标识，不能依赖之前定义的 API、SPEC 等别名。

卡片与契约缺失时先报告缺失材料；不要把整段作者聊天作为替代。新 Reviewer 可以读取需求、契约、差异和作者证据，但不继承作者的工作会话，也不把作者的结论当成已验证事实。

**相对路径不等于文件已经共享。** 总卡区分本地草案、已提交/可分发、接收方已可读取。Main 在允许的分发方式完成后核对接收方能读取约定材料；具体采用受控 Git 版本还是项目允许的文件交付方式由项目决定。生成 Skill 本身不执行分发、不写机器根映射、不把测试环境中的成功当作真实多机器验收。

## 任务包文件与事实归属

默认在一个任务包所属仓库创建：

```text
docs/task-packets/<parent-task-id>/
  packet.md
  main.md
  prompts.md
  workers/<task-id>.md
  reviews/<task-id>.md
  progress-state-contract.md
  dashboard/                 # 完整固定工具，含 panel_core/、resources/、README.md
  dashboard/index.html       # init 生成的独立离线快照
  runtime/plan.json          # 严格 planned 初始化输入
  runtime/panel.json         # CLI 创建的来源配置
  runtime/state.json         # 本地权威；projection 改为 view.json
```

`packet.md`：需求来源与覆盖、子任务索引、具体会话名册、执行/资源/速度三个策略轴及选择来源、模型目录快照、逐会话绑定、会话执行流程图、依赖/并行批次、适用阶段门禁、跨仓合并顺序、材料分发和执行前置条件。不是第二个活跃看板；若项目使用 Issue 维护活动状态，这里只引用 Issue，写生成时的明确快照。

`main.md`：Main 初始化、选定模式的实际调度规则、从资料恢复、派工与集成管理约定。`workers/`：每个 Worker 的实施约定。`reviews/`：对应独立 Reviewer 的审查约定。`prompts.md`：可复制的角色启动、恢复和适用阶段确认段落，不保存重复的长规格。

提示词同时交付于文件和最终对话：文件是可维护的资料来源，对话提供本次可直接复制的同内容副本。逐个列出真实 Task 对应的会话与短提示词，不只给文件链接或抽象的“Worker 模板”。每个段落说明会话名称、新开/续接及使用条件；首次 Worker/Reviewer 用独立会话，已有 Main、修复和复审按实际需要续接，不为每个动作额外创建会话。没有明确需求时不生成这些执行入口；用户明确缩小本轮交付范围时遵从其要求。

可按项目既有目录组织，不强制新建第二套文档。跨仓任务可以将子卡存于各代码仓库的既有目录，父卡只使用仓库标识和相对路径引用；不要为了方便复制产生多份权威卡片。所有文件路径必须在生成前确定并写入索引。

根据任务需要约定将来由执行者创建的报告位置，例如 `reports/<task-id>-handoff.md`、`reports/<task-id>-review.md`。生成阶段只登记位置，不生成看似已经执行的报告或虚假的 PASS。实现仓库与任务包仓库不同时，明确报告所属仓库及交付方式；不能让多个 Worker 同时写共享总卡或同一个报告。

每个包必须按 [进度面板接入](progress-panel.md) 复制固定 dashboard 和 v1 契约、生成 plan 并执行 init/status，交付 planned HTML；生成阶段不启动服务或角色、不编写网页代码。总卡和 Main 卡登记实际的面板/CLI/状态/配置/计划/契约路径、来源模式与权威引用；Main 卡包含可独立恢复的操作与错误处理规则。Python 3.11+ 是面板工具依赖，离线 HTML 查看无需 Python。

本地 source.reference 使用仓库标识与本包根相对路径，必须以 `runtime/state.json` 结束，便于工具限定包内证据。已有 Issue/YAML 权威使用 projection，view.json 与 HTML 仅是 Main 核对后的缓存，packet.md 仍是计划资料。所有实际 ID/模型/观察和证据在 planned 初始化保持空，检查各维度为 UNRUN；每任务分别登记非空 delivery、独立 review 及其他适用完成要求。

为每个具体 Worker/Reviewer（包括第二 Reviewer）分别实例化唯一报告仓库/相对路径、任务 round 与已有交付渠道。报告含 UTC 来源时间、进度/里程碑、阻塞、下一步、对应维度结果和证据，按轮次追加保留旧结论。角色只写自己报告、不写共享 state/view/panel 配置或调用 publish；Main 通过既有材料交付方式核对，不假定工作区共享。Main 启动、恢复、集成、阶段确认及各角色修复/复审提示词均含对应具体入口。

## 会话命名与执行登记

生成每个会话的确定名称，推荐「Task ID · Main/Worker/Reviewer · 具体工作内容」。例如 `M0-03 · Main · 文档导入统筹与集成`、`M0-03-01 · Worker · 导入 API 实现`、`M0-03-01 · Reviewer · 导入 API 独立审查`。角色名或编号不能代替工作内容；禁止仅使用 Main、Worker A、Reviewer 1 或“开发任务”等无法区分内容的名称。阶段 ID 可单独放在名册中，避免反复改名。

总卡名册登记完整会话名、Task ID、角色、实际工作内容、仓库、卡片相对路径、所属阶段、启动者与启动条件。卡片身份栏、提示词标题及首句、流程图标签使用同一名称。Main 的集成、Worker 的修复和 Reviewer 的复审只追加阶段说明，名称保持稳定；替换会话时保留逻辑身份并登记替换关系。

执行时可用工具支持命名则使用该名称；若标题被工具规范化，记录计划名与工具返回的实际名、会话 ID 的对应关系，后续调用使用实际 ID，不只按相似标题猜测。用户已有会话先建立映射，不能为符合模板而重复创建。生成阶段不虚构实际会话 ID，不修改无关会话名称。

执行模式及细则见 [执行模式约定](execution-modes.md)。将适用规则落实到 Main 卡及各角色身份/停止点，不能只在总卡写一个模式标签。会话名册是计划；实时会话 ID、授权阶段和执行证据使用一个明确的权威状态来源维护。

## 模型资源与速度绑定

模型资源和 Fast 规则见 [模型资源与速度策略](model-and-speed-policies.md)。执行模式、资源档位和速度策略分别登记，不相互推导。总卡保存生成时的目录来源、检查时间、宿主适用范围、计价信息状态和单会话服务层能力；它们是会变化的计划依据，不是永久型号排名。

Main、每个 Worker 和每个 Reviewer 都必须在名册或紧邻的绑定表中拥有准确 `provider`、`model`、`reasoning_effort`、`service_tier`、选择理由、有序回退、升级触发条件和有限上限。卡片与短提示词引用同一绑定。即使 `fixed-main` 选择与 Main 相同的配置，也要写出准确值，不能用“同 Main”或省略创建参数代替。

生成宿主无法看见实际模型目录时，允许先写完整任务拆分，但整个任务包必须标为 `MODEL_BINDING_BLOCKED`，不得声称可派工。Main 启动后先在执行宿主解析并写回所有准确绑定，完成复核后才将包改为 `ready_for_dispatch`。第三方模型、推理强度、上下文能力、费用和 Fast 支持均以当前可验证信息为准，未知项不靠名称推断。

每次创建新会话时显式传入工具支持的绑定字段，并在活动状态记录计划值、实际值和所用回退。宿主不支持单会话字段时记录实际控制层；关键路径 Fast 无法局部应用时按约定使用标准层，不能悄悄扩大成全局 Fast。续接、升级和重试遵循卡片上限。

## 可执行粒度与验收

叶子任务同时具备：一个可观察结果、一位实现责任角色、明确输入/输出、写入范围、可用依赖、可验证验收、独立审查对象和交接停止点。设置、测试、必要文档和相关修复通常跟随该结果。只有两个结果可以独立接受或拒绝时才拆开。

每条验收写成「输入/前置 → 操作 → 预期结果 → 验证方法 → 证据」，覆盖需求中所有适用的正常、边界和拒绝行为。命令说明所属仓库、相对工作目录、环境前置条件、期望结果；以现有文档/配置为依据。新测试列出计划创建文件、具体断言及届时可执行的仓库测试命令，不伪装成已有测试。

如果暂时只能执行静态检查、Fixture 或 Fake，就写明其证明范围与仍需实机/真实服务的证据。业务测试在生成阶段通常为 UNRUN。已知环境准备可登记为执行前置条件；范围、外部约束或验收标准未知则回到需求澄清。

记录依赖条件，例如已批准契约、提供方接口可用、指定制品可获取；不能只写另一个 Task ID。跨仓依赖使用项目批准的契约/制品方式。公共文件、公共环境或数据资源设置单一写入者或串行批次。

## 会话执行流程图

每个就绪任务包在总卡中提供 Mermaid `flowchart TD`，并在最终对话的提示词之前展示同内容的 `mermaid` 代码围栏。默认直接使用 Markdown 中的 Mermaid，不依赖图片生成、外部制图服务或第三方 Orchestrator。流程图表达计划执行关系，不能把节点画成已经完成或已经批准。

- 用真实 Task ID、会话名称和阶段标注每个会话节点，与具体启动提示词一一对应；生成的任务包不能保留抽象的 Worker A/B 或模板变量。一个会话可以有多个阶段节点，但必须使用相同的会话名称并注明续接。
- `assets/packet.md` 使用可渲染的 `TEMPLATE` 预览节点，避免未实例化模板在 Markdown 查看器中触发 Mermaid 语法错误。生成正式任务包时必须把该节点整行替换为具体流程；最终图不得保留 `TEMPLATE`、Mustache 变量或其他生成说明。
- Main 的规划、恢复和集成是同一角色的不同阶段；已有 Main 优先续接。Worker 与 Reviewer 首次启动是相互独立的新会话；修复继续原 Worker，复审继续原 Reviewer。需要替换会话时注明从任务资料恢复，不能把每次操作都画成新建 Session。
- 实线箭头表示正常执行顺序，边上注明关键启动条件；只将依赖已满足且写入无冲突的任务画成可并行分支。跨仓任务的契约、提供方、消费方和集成顺序必须与总卡一致。
- 用虚线回边表示审查未通过后退回原 Worker 修复；修复完成后仍须回到对应 Reviewer 复审。任务前置依赖必须无循环，这类修复/复审控制回路不属于循环依赖。
- 多分支汇合处显式标注“全部所需前置条件满足”，不能让图看起来任意一个 Reviewer 通过即可开始集成。检查或汇合节点标为条件，不计作新会话；项目要求的人类审批标明为人类门禁，不能用 AI Reviewer 通过替代。
- 只画本任务实际需要的步骤，末端与任务卡约定的停止点一致。需要另行授权的后续步骤应标为等待条件，不暗示生成任务包就已获准合并或发布。图中涉及文件的引用也遵守仓库标识与相对路径约定。
- 图中明确模式与推进责任：全自动标明 Main 自动调度；人工标明每次启动/续接由用户触发；半自动以阶段分组，阶段内由 Main 推进，跨阶段必须经过用户确认节点。原有项目批准节点在三种模式下均保留。
- 使用 `critical-path` 或 `fast-all` 时，可在实际请求 Fast 的会话标签后加 `⚡`，并在图例说明；没有标记的会话使用标准服务层。Fast 标记不表示模型能力、任务优先级或完成状态。

图旁用简短文字说明可并行批次、实线/虚线含义和会话复用规则；详细依赖证据与验收标准留在任务卡。不要用流程图代替任务卡或每个会话独立可复制的提示词。

## 角色、生命周期与证据

### Main

长期保留角色职责，允许更换会话。通过总卡、Issue、提交/差异、报告与项目规范恢复；不要求无限保留聊天。负责范围与依赖、证据核对和集成管理，不编写 Feature。按模式控制调度：全自动接管计划内流程，半自动仅推进获准阶段，人工只交付下一会话提示词并等待用户启动。正常机械集成按授权执行；需要业务语义修改时退回对应 Worker，必要时为集成修复单列任务。

### Worker

一个 Task 使用独立分支、worktree 和会话，保留已有用户改动。执行具体卡片，编写适用测试，在授权范围内本地提交；默认不推送、不创建 PR、不合并。交付文件、行为变化、验证命令/结果、未解决事项和可复查实现对象，然后进入待审。审查发现问题后继续本任务修复，不接入无关新任务。

### Reviewer

独立 Session 与隔离审查工作区，明确检查哪个实现对象。需求审查、实现审查与证据复核缺一不可；执行可用且适用的独立验证。不修复产品代码，不替 Worker 提交；审查探针只放隔离位置，报告按卡片范围交付。`assured` 对关键任务安排两个 Reviewer；`maximum` 为每个叶子任务安排两个 Reviewer，其中一个明确负责对抗性边界/安全审查。每个 Reviewer 都有独立名称、卡片、提示词和模型绑定。

问题采用项目既有分级，至少记录影响、文件相对位置、复现/推导依据、预期/实际行为、修复要求与验证方式。技术通过要求项目定义的阻断问题关闭且所需验证有证据。不要把某次任务的特殊 P1/P2/P3 零问题阈值、禁止哈希要求或模型选择固化成所有项目的规则；当前用户明确要求的例外应原样进入本任务并指出影响。

修复由 Worker 完成，再交原 Reviewer 复核定向问题及受影响回归。Reviewer 会话不可用时，用明确审查对象、原始问题与报告移交新的独立会话。实现对象或验收约定变化时，旧审查结论不能自动覆盖新内容。按项目允许方式标识审查对象，不强制采用哈希，也不在禁止哈希的任务中换用另一种哈希。

### 集成与结束

按依赖顺序核对 Worker 交付、独立审查、适用人类批准、集成回归、合并/发布证据。AI 技术通过不替代项目规定的人类批准。Local、CI、实机/共享环境、合并、部署、验收分别报告，不能由其中一个通过推断其他通过。

Worker 提交后仍须处理本任务修复；闭环交接后可归档会话。归档 Session、清理 worktree、删除分支分别处理，生成 Skill 不执行清理。

## 生成后的检查

- 核对固定工具及包内契约完整、init/status 实际成功、seq=0/planned、HTML 已生成、无实际会话或批准/执行证据、未启动服务；模型阻塞仍保留 MODEL_BINDING_BLOCKED。来源锚点与报告入口一致，投影不夺取原权威。已存在的状态保留而不重新 init，恢复与显式 run.start 重跑分开。
- 每条需求映射到叶子任务和验收；每条任务前置依赖可理解、无循环，流程图的修复/复审回路单独检查。
- 并行任务的文件与共享资源无写入冲突。
- 每个 Worker 对应独立 Reviewer 卡；Main 的集成与恢复有入口。每个会话均有体现任务内容的唯一名称，名册、卡片、提示词和图一致，续接动作不冒充新会话。
- 核对三种模式的推进责任：全自动 Main 有明确调度授权；人工不自动创建、委派或发送触发执行的续接消息；半自动有具体阶段、验收、后续阶段确认提示词及不可自动越过的门禁。未指定模式默认人工，只有任务较多时主动建议半自动。
- 核对 `execution_mode`、`resource_profile`、`speed_policy` 三个独立轴及选择来源；未指定资源/速度时明确使用 `balanced + standard`，`fast-all` 具有用户明确选择依据。
- 核对 Main 与每个 Worker/Reviewer 的准确提供方、模型、推理强度和服务层；主选与回退存在于本次目录快照，创建提示词不依赖 Main 默认继承。准确值尚未解析时，整个包保持 `MODEL_BINDING_BLOCKED` 且不能派工。
