# 任务包独立 HTML 进度面板设计

日期：2026-09-08

适用范围：本仓库维护的 `skills/plan-agent-tasks/`。

文档状态：用户已于本会话确认整体设计，进入实现计划阶段；尚未实现、运行或验收。

## 1. 已确认的需求与本稿建议

用户已经确认：

- 每个任务包拥有独立 HTML 面板，展示本任务包的完成情况、活跃工作和执行流程。
- Main 统一维护共享状态，Worker 和 Reviewer 分别提供自己的进展与证据。
- 页面自动更新；Main 自动启动轻量本地预览并提供入口。
- Main 在关键执行事件后更新，等待期间目标每 30 秒核对一次；浏览器每 2 秒检查新数据，实际采集频率受宿主能力约束。
- 显示最后同步时间和任务最近进展时间；旧状态不能冒充当前状态。
- Worker 交付、独立审查通过、任务完成分别记录。
- Main 恢复时延续原面板；结束后保留可离线打开的最终快照。

整体确认包含本稿补充的默认设计：复用工具与固定网页模板、任务为主节点的页面布局、状态分类、失去更新的提示条件、数据契约、预览运行依赖和降级处理。

## 2. 目标与边界

用户打开一个任务包的面板后，应能回答：哪些任务已完成，谁在工作，当前在实施还是审查，什么阻碍了后续任务，哪里需要用户决定，以及最近发生了什么。

第一版聚焦单个任务包。页面提供观察、筛选、展开和证据定位；派工、返修、阶段批准及其他执行操作仍由 Main 按任务卡处理。面板不提供执行按钮，不接管调度，不创建跨项目聚合平台，也不新增跨机器通信服务。

任务包生成阶段只生成结构与面板材料，初始状态为尚未启动；不会因为生成 HTML 而启动 Main、会话或预览进程。

面板适用于现有三种模式：自动模式显示 Main 的调度进展；半自动明确显示当前批准阶段和下一阶段门禁；人工模式明确显示等待用户启动或续接，不把等待写成失败。

本设计沿用本次任务的禁止 SHA 检查要求；面板、恢复和验收均不新增此类检查。

## 3. 数据维护方案选择

| 方案 | 优点 | 代价与适用性 |
| --- | --- | --- |
| Main 汇总，角色各自报告（采用） | 与现有调度和单一写入者规则一致；任务完成可由 Main 核对证据后确认 | 更新时效依赖 Main 获取并处理报告 |
| 所有角色共同修改共享状态 | 角色事件可以直接进入页面 | 需要处理并发冲突、越权完成和隔离工作区同步，不适合第一版 |
| 独立采集服务连接宿主 | Main 暂停时仍有机会读取会话状态 | 增加宿主适配、权限和运行生命周期，暂不引入 |

采用 Main 汇总方案。预览服务只负责读取与展示，不连接宿主、不代替 Main 推断执行结果。

### 3.1 工具生成页面，Agent 只提供数据

采用随 Skill 分发的固定网页模板与工具。生成任务包的 Agent 和执行中的 Main 均不重新编写 HTML、CSS、JavaScript 或图布局代码；提示词只约定数据内容、工具调用时机和失败处理。

| 时机 | Agent 提供的内容 | 工具负责的动作 |
| --- | --- | --- |
| 生成任务包 | 结构化任务名册、角色、依赖、阶段和门禁 | 复制固定版本资源，校验计划数据，生成独立 HTML 和未启动状态 |
| Main 启动或恢复 | 本任务包入口及核对后的初始或恢复数据 | 校验状态，生成快照，启动或复用本地只读预览 |
| 执行状态变化 | 有变化的任务、角色、阶段字段，事件编号及证据引用 | 校验并合并更新，发布完整状态与 HTML 快照，供浏览器读取 |
| 执行结束 | Main 核对后的最终状态 | 导出独立离线 HTML，确认可读取后关闭本包预览 |

首次初始化输入完整计划数据；后续发布只需提供结构化增量及预期状态序号，避免 Main 为一次任务变化重写整份状态。工具负责机械合并、重复事件识别、序号与格式校验；任务是否满足完成条件仍由 Main 根据证据判断，工具不从聊天文本推测业务结论。

结构化操作包括 `task.set`、`session.set`、`stage.set`、`check.set`、`evidence.put`、`main.set`、`source.set`、`packet.set`、`plan.replace`、`run.start`。其中 `packet.set` 的 changes 只允许 stage_id，值为已登记阶段 ID 或 null，用于切换或清除当前阶段展示；它不批准阶段、不改变执行授权，也不允许修改任务包身份、模式、lifecycle、运行号、计划修订号或来源。Main 状态到 lifecycle 的既有映射保持不变。

已有外部权威来源时，Main 先按原流程写回并核对来源，再提交对应展示更新；工具仍只维护展示投影。Main 是状态决定者和唯一调用写入入口的角色，实际文件写入由工具完成。

这里的工具优先实现为可随任务包复制的本地命令行程序，不要求注册专用 MCP 服务。具体子命令和参数在实现计划中确定。工具发布完整状态文件，浏览器直接渲染其数据；离线 HTML 的更新也是固定模板填入数据的确定性操作，不消耗模型调用来重新设计网页。

各任务包使用同一套已验证模板，各自持有独立副本、数据和运行实例。工具版本与数据格式版本分别登记；后续升级模板需显式更新资源，不在运行中让 Agent 临时修改网页代码来适配数据。

## 4. 页面结构

### 4.1 顶部总览

展示任务包名称、执行模式、当前阶段、Main 的登记状态、任务统计和数据新鲜度。统计以叶子任务为单位，不把 Worker、Reviewer、Main 或门禁节点混入任务总数。

核心统计为已完成、进行中、待审查、等待确认、受阻和未开始；失败、取消在发生时单独显示。阶段门禁单独展示，不计入任务数量。

默认显示完成任务数与纳入计划的任务总数，不展示推算的工作量百分比、预计完成时间或未经宿主提供的费用。取消任务单独列明，并从完成比例的分母排除。

### 4.2 流程图

默认以任务为节点，按阶段分组，从上到下呈现前置依赖和可并行分支；条件汇合与用户门禁使用独立形状。节点显示 Task ID、简短名称、文字状态和当前角色活动摘要。

颜色辅助识别，所有状态同时提供文字或图标。支持缩放、平移、适应画布，以及只突出活跃、受阻或当前阶段的任务。筛选时保留必要的前置关系，避免误导依赖含义。

任务前置依赖保持无环；Worker 与 Reviewer 的修复、复审轮次在节点详情中展开，避免把返修控制回路误当成新的任务依赖。已有任务包 Mermaid 会话图继续保留；面板任务图是同一计划的另一种展示，两者的任务、依赖和门禁必须一致。

支持一项任务有多个 Reviewer。Reviewer 的逻辑身份、实际会话映射和独立结论分别保留，不能合并成一个未经证据支持的通过状态。

### 4.3 节点详情与活跃任务

选择任务后展开详情：目标、当前步骤、依赖是否满足、Worker 与各 Reviewer 的状态、已登记模型配置、返修轮次、最近进展、阻塞原因、下一步和证据入口。

计划模型与实际采用模型分别显示；实际值未取得时明确写未确认。会话 ID 只采用宿主实际返回的值；名称稳定，会话替换保留前后映射。

活跃任务列表提供简短入口，显示具体活动，如实施、测试、审查或返修。会话已结束而任务仍待审时，任务不会计为已完成。无法取得宿主当前状态时，活跃信息必须带最后观察时间。

### 4.4 最近动态

按时间显示派工、角色进展、交付、审查结果、返修、阻塞、阶段批准和完成等事件。展示结构化摘要及证据引用，不复制完整聊天或逐 token 输出。

自动更新保留当前选中节点、缩放和滚动位置。提供对应的任务列表作为图形不可用时的可读入口；错误信息不能覆盖最后一次有效数据。

## 5. 数据归属与文件结构

沿用项目已有任务目录；缺省任务包仍位于 `docs/task-packets/<parent-task-id>/`。新增内容随任务包分发，运行时不能依赖个人 Skill 安装目录或本仓库根脚本。

建议结构如下，尖括号表示任务包生成时确定的具体名称：

```text
docs/task-packets/<parent-task-id>/
  packet.md
  main.md
  prompts.md
  workers/
  reviews/
  reports/
  runtime/
    state.json                  本地权威状态模式使用
    view.json                   既有外部权威来源模式使用
  dashboard/
    index.html                  独立 HTML，包含最近一次嵌入快照
    panel.py                    状态校验、快照生成及只读预览工具
    resources/
      panel-template.html       固定网页模板，包含离线所需样式与渲染逻辑
    README.md                   打开、恢复及运行依赖说明
```

`state.json` 与 `view.json` 按模式选择，不同时充当权威来源：

1. 项目没有已有权威状态位置时，Main 单独维护 `runtime/state.json`，页面和恢复流程读取它。
2. 项目已有 Issue、项目系统或约定文件时，继续沿用该权威来源。Main 写回并核对来源后生成 `runtime/view.json`，它明确标为展示缓存，记录来源和读取时间，不用于覆盖权威来源。
3. 已有文件可以扩展时，优先原地补充必要字段，避免无意义迁移。来源与本地展示契约不同的，由 Main 读取材料后形成投影；第一版不开发平台连接器。

HTML 内嵌数据和 `view.json` 都属于可再生成的展示副本，不是第二套活动状态。计划仍由任务卡定义；状态中保存显示所需的任务与依赖投影及计划修订编号。Main 修改计划后同步该投影，不让浏览器自行解析任意 Markdown 来猜测计划。

Worker、Reviewer 在各自被授权的仓库和隔离工作区写各自报告。Main 通过现有会话返回、报告分发或已授权读取渠道取得材料；不能假定其他 worktree 或机器的文件会自动出现在 Main 工作区。

角色报告分别命名，包含 Task ID、角色身份、工作轮次、报告时间、进展摘要、阻塞、结果和证据引用。Main 未取得角色的新报告时，显示最后收到的材料及时间；不能伪造心跳。

## 6. 状态契约与完成口径

状态格式带显式版本号。每份有效快照至少包括：

| 对象 | 必要内容 |
| --- | --- |
| 任务包 | 稳定任务包 ID、计划修订编号、运行次数、执行模式、当前阶段、当前批准范围、约定停止点 |
| 数据来源 | 权威来源类型及引用、此次快照序号、生成时间、Main 最近成功核对时间、来源可用性 |
| Main | 逻辑身份、实际会话映射、运行中／等待用户／受阻／已结束等登记状态及观察时间 |
| 任务 | Task ID、名称、阶段、依赖、调度状态、最近进展、阻塞原因、下一步、完成条件与证据引用 |
| 角色会话 | 逻辑角色 ID、角色类型、计划与实际会话名称、实际会话 ID、宿主状态及观察时间、工作轮次、计划与实际模型绑定 |
| 验证与门禁 | 实施交付、各 Reviewer 结论、所需批准、集成、测试及验收等适用要求，各自的结果、适用工作轮次和证据 |
| 动态 | 稳定事件编号、事件时间、Main 收到时间、对象、类型、摘要和来源引用 |

任务调度状态与验证结论分开。默认任务状态为：

| 状态 | 含义与统计归属 |
| --- | --- |
| `pending` / `ready` | 未开始；详情区分等待前置条件和已可派工 |
| `implementing` / `fixing` / `validating` | 进行中；当前在实施、返修或集成验证 |
| `awaiting_review` / `reviewing` | 待审查；详情区分等待 Reviewer 和正在审查 |
| `waiting_approval` | 等待任务所需的人类决定；阶段级等待另记阶段门禁 |
| `blocked` | 当前无法推进，必须说明阻塞原因 |
| `failed` | 已有明确失败及停止依据；不能由旧时间戳推导 |
| `done` | 满足本任务卡全部适用完成条件 |
| `cancelled` | 依据已记录的范围决定取消，单独统计 |

验证结论使用 `PASS`、`FAIL`、`UNRUN`、`BLOCKED`，只在相应验证维度使用；不适用的条件明确标为不适用并说明依据。测试失败且可修复时，任务可以进入返修，不能据此认为整个任务包已经终止。

Worker 交付后通常进入待审。Main 核对全部所需 Reviewer、批准及本任务约定的集成或验收条件后，才登记 `done`。任务不要求的合并或部署，不额外添加为完成门槛。

发生返修或范围变化时，提升工作轮次或计划修订编号，标明受影响的旧结论需要重新核对；保留历史结果，不让旧 PASS 自动覆盖新实现。任务重新打开时，完成计数允许相应减少，并显示原因。

依赖是否就绪按任务卡约定的具体前置条件计算，并在详情中显示条件；不简单假设所有依赖都必须等到最终合并，也不把任意一个 Reviewer 通过视为全部前置满足。

## 7. 更新、读取与可信度

Main 在派工、接收进展、交付、审查、返修、批准、受阻和结束等关键事件后更新。在能够继续执行的等待期间，目标每 30 秒核对一次活跃角色；优先宿主事件等待和紧凑状态查询，避免重复聊天追问。

30 秒是正常条件下的采集目标，不是跨宿主保证。Main 处于长工具调用、等待用户或会话中断时，不能保证继续采集。已知等待用户应显示等待状态；失去同步仅提示信息可能过期，不自动判定任何角色失败。

浏览器每 2 秒向本任务包预览服务读取最新有效快照。没有新序号时保持当前展示，不重建图；不会通过再次读取旧快照刷新 Main 核对时间。

页面分别展示：

- 页面最近一次成功读取服务的时间：反映预览连接。
- Main 最近成功核对执行状态的时间：反映来源新鲜度。
- 各任务最近一次实质进展的时间：反映工作进展。

默认主动作业状态超过 120 秒未获 Main 核对时，显示“状态未及时同步”和实际时间差。等待用户、任务包已结束和离线快照使用各自明确提示；长期无实质进展本身不等于失联，也不触发自动终止。

写入工具校验任务引用、状态、版本和单调递增序号后，以同目录临时文件加替换方式发布完整快照。Main 对同一任务包的写入串行化；替换 Main 后必须先确认旧 Main 已停止维护，再接管同一来源。工具应拒绝已知的旧序号写入并检测重复本地写入，不能靠“最后写入覆盖”解决冲突。

预览端读取到不完整、格式无效、版本不支持或引用错误的数据时，保留上次有效快照并显示具体同步错误，不清空面板、不将缺失数据解释为零个任务。事件按稳定编号去重；源事件时间与 Main 接收时间分开，避免把延迟报告当成刚刚发生的工作。

本地单写入者保护不承诺提供跨机器分布式锁。Main 迁移遵循显式交接，同一任务包同一时刻只能有一个被指定的状态维护者。

## 8. 独立预览与离线快照

每个任务包拥有自己的 HTML、数据和预览进程，独立选择可用本地端口；关闭一个面板服务不影响另一个任务包。链接可以因服务重启改变，任务包身份和面板文件路径保持稳定。

建议实现采用 Python 3.11+ 标准库提供本地只读预览和状态工具，前端资源随包携带，不依赖 CDN、联网字体或在线绘图库。运行时不要求用户安装 Node.js、包管理器或全局 Web 服务。

这是实时面板新增的运行依赖，需要在 Skill 和生成包中明确说明；不能继续笼统宣称全部执行功能无需 Python。单独查看已经生成的 HTML 快照不需要 Python。

Main 首次启动时校验面板材料与运行能力，生成首份状态，后台启动预览，确认读取成功后提供访问链接；有宿主打开页面能力时打开该链接。Windows 后台进程采用隐藏窗口方式启动。恢复时先验证现有服务属于本任务包且响应正常，再决定复用或重启，避免只凭旧 PID 或旧端口判断。

只监听本机回环地址，只提供面板、有效快照及明确登记的包内查看资源，不暴露整个仓库目录，不提供写入或执行接口。敏感内容和原始聊天不进入面板；展示的角色文字按文本处理。证据采用仓库标识与仓库内相对路径或真实远程 URL。

本机可读取且明确登记的包内证据提供查看入口；跨仓或其他机器材料不保证可直接打开，显示仓库、相对路径和可复制定位信息。离线 HTML 中仍显示证据定位，只有实际随包携带的材料才承诺可读。

Main 每次发布有效状态后生成包含完整展示数据的 HTML 快照。直接打开 HTML 时使用内嵌数据，明确显示“离线快照”和生成时间；经本地服务打开时读取新状态。前端样式、图形和必要脚本全部可离线运行。

Main 正常结束时先写最终状态并确认最终 HTML 已生成，再关闭自己的预览进程并给出离线文件入口。Main 异常中断时可能留下预览进程或较旧的 HTML；服务只展示现有数据，页面依靠时间提示说明缺口，恢复时由 Main 核对并处理。

预览启动失败、运行依赖缺失或 HTML 更新失败时，Main 显示“面板不可用”或“快照未更新”及原因。观测故障不自动中止已有授权业务，也不能被隐瞒为实时面板成功；用户仍可从任务卡、状态来源和报告查看进度。

## 9. Main 初始化与恢复流程

1. 读取任务卡、执行模式、权威来源和面板配置，识别是首次运行、恢复还是明确的新一轮执行。
2. 恢复时确认已有会话、已完成动作、工作轮次和批准范围；不因为面板缺失或损坏而重复派工。
3. 核对计划与状态引用，更新首份有效显示数据；未确认的宿主状态显示未知及最后观察时间。
4. 启动或复用本任务包预览，验证数据与任务包身份，提供链接。
5. 按当前授权模式推进任务，依据事件和适用等待周期核对并发布状态。
6. 正常结束时固化最终结果与剩余条件，验证离线快照，再停止该任务包的预览服务。

单纯恢复不增加新的执行次数，不重置完成状态。用户明确重新执行时登记新运行次数，保留上一轮结果；旧会话结论不能不经核对直接复用。

## 10. Skill 改动范围

后续实施将修改 `SKILL.md`、执行模式与任务包契约引用、Main/Worker/Reviewer/总卡/提示词模板，以及使用说明和示例。补充独立可分发的固定面板模板、状态工具和相关验证；先维护一次通用实现，再由所有任务包复用，不能把页面实现责任交给每次执行任务的 Agent。

Skill 规则应具体要求角色在有意义的里程碑报告进展，而不是要求每条消息、每个命令都写共享状态。Main 的进展采集与单一写入者职责写入生成后的 Main 卡，Worker/Reviewer 的报告位置和传递约定写入各自卡片。

任务包生成阶段记录未启动状态并检查任务图一致性；Main 启动提示词明确初始化本任务包面板。恢复与阶段确认提示词保留原有模式和批准边界，面板配置不会扩大执行授权。

根仓库仍只是维护源，分发 ZIP 必须包含面板所需全部资源与许可。任务包实例也须脱离 Skill 安装目录运行；生成后的路径均采用清楚锚定的相对路径。

## 11. 验收方案与证据等级

| 场景 | 可观察预期 |
| --- | --- |
| 生成任务包 | 具有独立 HTML 和必要材料；只显示计划，未启动会话或服务 |
| 固定工具与模板复用 | 使用不同的结构化任务数据生成两个独立面板，均不需要模型编写或修改网页代码；相同工具版本及输入得到一致的展示内容 |
| 增量发布 | 一项任务的有效更新只改变指定字段及相关派生展示；重复事件不重复计数，过期序号不覆盖新状态，其他任务保持原值 |
| Main 启动 | 返回本任务包有效本地入口；任务名称、阶段、依赖与任务卡一致 |
| 正常执行 | Worker 运行、交付、Reviewer 审查、完成按证据依次显示 |
| 返修与多 Reviewer | 每位 Reviewer 分开显示；旧结论不会覆盖新轮次；未满足全部完成条件不计为完成 |
| 阶段与人工模式 | 等待用户或阶段确认清楚可见，页面不会触发派工或批准 |
| 角色文件隔离 | Main 能通过约定报告渠道取得材料；不依赖 worktree 或跨机器文件自动共享 |
| 更新时效 | Main 已成功发布的新快照，在正常前台本地浏览条件下 5 秒内可见；Main 的 30 秒核对目标单独记录实际达成情况 |
| 数据停更 | 服务仍可访问时仍能发现 Main 数据已过期；不误判任务失败 |
| 数据异常 | 损坏、未知版本、旧序号或缺失引用产生错误提示，保留最近有效展示 |
| 恢复与去重 | 延续同一面板和执行记录，不重复派工或重放动态，不越过批准阶段 |
| 两个任务包并行 | 页面、数据和端口互不串用；停止其中一个不影响另一个 |
| 离线快照 | 正常结束后关闭服务，断网直接打开 HTML，仍能查看最终流程、状态和证据定位 |
| 分发与迁移 | 复制生成包到另一目录后可启动，前端无外部网络请求，不需要原 Skill 安装位置 |

按实际证据分别报告：文档与结构检查、工具与浏览器验证、生成包迁移验证、真实 Main/Worker/Reviewer 运行验收。模拟事件能证明展示逻辑，不证明宿主真实调度、跨机器报告传递或实际执行时效。

第一版真实验收以当前宿主和本地生成包为范围。其他宿主、跨机器并发及外部状态系统适配未实际验证时记为 `UNRUN`，不能根据通用 Markdown 或模拟状态外推兼容结论。
